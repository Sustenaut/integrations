## 0.16.0 - 2026-11-19

Commit `8beb1d984eff`; release record `pub:sha2-256:3df3vq3w3wmmbdnp3kvex5uvxapx6txbimbnw7tnikepngiwsr7q`.

### Changed
- The platform's nightly pubrules checks move to their new names: INGEST_PUBRULES_CHECKS (was INGEST_PUBKIT_CHECKS) names the pubrules-checks tenant, whose files load into platform.pubrules_checks (was pubkit_checks)
- A Caller given no transport (in JS, no fetch) now calls through the current transport, the network unless INTEGRATIONS_MODE or a test harness says otherwise; and a mode other than live without PUBTEST_RUN makes every call refuse to start

### Removed
- Replay and Recording are gone: use integrations.transports' Cassette and Recorder (one import to change); Cassette still reads the old {"responses": …} files

### Added
- Record and replay: integrations.transports (and transports.js) with Cassette, Recorder, Faulty, current_transport() and use(), the integrations.cassette/1 format with its baseline and promote(), a plugin's record block and plugins/_github.json, Caller.opener and caller.fetch, and the opt-in integrations.testing pytest plugin

### Fixed
- integrations ci-usage jobs keeps its state (the job ids written) to the look back on every save, so it stays well under storage's 1 MiB for a file: the 90-day backfill's state outgrew it and storage refused the save (413). Jobs a pass writes are also kept in memory for that pass, so a run two days' queries both list is written once

### Internal
- pubkit is now pubrules: the repository runs on pubrules 0.43.0 (pubrules.json, ./pubrules, the managed workflows and test pins)
- The test suite's scenarios, Python and JavaScript, are Given/When/Then on pubtest's steps

## 0.14.4 - 2026-11-16

Commit `cd299d5b74c3`; release record `pub:sha2-256:p6aes64wf3pvc2sa2q7uslxgx5ah773j7ybnv7ri47l2citilina`.

### Added
- integrations ci-usage: CI's wait times and compute load for platform.ci_jobs and platform.cluster_usage, through storage's ci-usage buffer. `jobs` (k8s/ci-jobs.yaml, every ten minutes, as the release reader app) writes each finished GitHub Actions job of the board's repositories once, with wait_seconds and run_seconds, its state a head in the ci-jobs tenant; `--since-days 90` backfills. `cluster` writes the k3s server's node, namespace, ci (quota, runners) and runner rows, with each runner pod's cgroup memory.peak; avrofile has encode_ci_jobs, encode_cluster_usage and their decoders
- The ingest pod loads any number of buffers more: INGEST_BUFFERS, [{"tenant": ..., "dataset": ..., "table": ...}], so one dataset holds several Kinds (platform's ci_jobs and cluster_usage, both from the tenant ci-usage, beside pubkit_checks); Kinds sharing a tenant keep their batch records apart (batches/<table>-). INGEST_SIGNALS, INGEST_NEED_STATES and INGEST_PUBKIT_CHECKS work as before

## 0.14.2 - 2026-11-13

Commit `a47adea4b9ea`; release record `pub:sha2-256:cc6zdjv3hakloetr7ma6j6clpmsl6cdxzjqpdbcdjs37r2sgsbgq`.

### Added
- The ingest pod loads the convergence engine's need states: INGEST_NEED_STATES, {"tenant": ..., "dataset": ...} like INGEST_SIGNALS, from inbox/need-states/ into the dataset's need_states table; avrofile has encode_need_states and decode_need_states

## 0.14.1 - 2026-11-06

## 0.14.0 - 2026-11-06

Commit `7e3a4604deaf`; release record `pub:sha2-256:pecxorr363weqbmckyftckktf5milea3536l5nlurhc44vyf37ta`.

### Changed
- StorageSink sends its files through the storage client, as storage.api's sink operation: tried once, for up to a minute, and not recorded, as before
- A sink's timer sends its first file a random part of a cycle in, so pods started together don't send at once

### Added
- A registry operation may name its own timeout and tries, in place of its class's
- Storage clients, clients/js/storage.js and integrations.clients.storage, generated from Sustenaut/storage's openapi.json as vendored and pinned in openapi/storage.json, as plugin storage.api
- Unavailable carries the last response, and a Replay answer may give its ETag
- A retry waits a random time up to 2**n s (full jitter) or what a 429's or 503's Retry-After says, up to the class's timeout, and a call never runs past its timeout times its tries, in calls.py and caller.js
